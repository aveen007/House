# Stress Testing (5.2.7)

## Описание

Stress Testing определяет пределы устойчивости системы, точку отказа и характеристики восстановления.

## Требования из TestPlan

- **Нагрузка по шагам**: 50, 75, 100, 125, 150, 200 пользователей
- **Каждый шаг**: 
  - Ramp-up: 3 минуты (180 секунд)
  - Hold: 10 минут (600 секунд)
  - Total: 13 минут (780 секунд)
- **Распределение пользователей** (пропорционально Load Testing):
  - 50 users: 20/15/10/5 (View/Manage/Bets/External)
  - 75 users: 30/22/15/8
  - 100 users: 40/30/20/10
  - 125 users: 50/37/25/13
  - 150 users: 60/45/30/15
  - 200 users: 80/60/40/20

## Критерии успеха

- Идентифицирована точка деградации
- До точки деградации система ведёт себя предсказуемо (латентность растёт плавно)
- После снятия нагрузки система восстанавливается ≤10 минут (предпочтительно) или ≤2 часа (NR-02)

## Точка деградации

Тест останавливается, когда:
- Процент ошибок 5xx > 5%
- ИЛИ latency p99 > 30 секунд

## Способы запуска

### Способ 1: Автоматический скрипт (рекомендуется)

```bash
cd /Users/daniel/Documents/programming/mpi_proj/House/jmeter-tests
./run_stress_test.sh
```

Скрипт автоматически:
1. Запускает тест для каждого уровня нагрузки (50, 75, 100, 125, 150, 200)
2. Модифицирует тест-план для каждого уровня
3. Собирает результаты
4. Определяет точку деградации
5. Создает summary CSV файл

### Способ 2: Ручное создание тест-плана в JMeter GUI

1. Откройте `stress_test_plan_base.jmx` в JMeter
2. Для каждого уровня нагрузки (50, 75, 100, 125, 150, 200):
   - Создайте 4 ThreadGroup (View, Manage, Bets, External)
   - Установите количество потоков согласно распределению
   - Установите ramp-up: 180 секунд
   - Установите duration: 780 секунд
   - Используйте "Start Time" для последовательного запуска (опционально)
3. Сохраните как `stress_test_plan.jmx`

### Способ 3: Запуск отдельных шагов вручную

Для каждого уровня нагрузки:

```bash
# Модифицировать тест-план для нужного количества пользователей
# Затем запустить:
jmeter -n -t stress-test/stress_test_plan.jmx \
  -l results/stress_50users_$(date +%Y%m%d_%H%M%S).jtl \
  -e -o results/stress_50users_report_$(date +%Y%m%d_%H%M%S)/
```

## Мониторинг

Во время теста мониторьте:

1. **JMeter Metrics**:
   - Latency (p50, p90, p99)
   - Error rate (4xx, 5xx)
   - Throughput

2. **System Metrics**:
   - CPU usage
   - Memory usage
   - Database connections

3. **Application Logs**:
   - Ошибки в логах Spring Boot
   - Database connection pool exhaustion
   - Out of memory errors

## Результаты

Результаты сохраняются в:
- `results/stress_step_*users_*.jtl` - JTL файлы для каждого шага
- `results/stress_step_*users_report_*/` - HTML отчеты
- `results/stress_test_summary_*.csv` - Сводная таблица

## Интерпретация результатов

1. **Точка деградации**: Первый шаг, где error rate > 5% или p99 > 30s
2. **Восстановление**: После снятия нагрузки система должна вернуться к нормальным показателям (p90 ≤ норм, errors < 1%) в течение 10 минут

## Примечания

- Тест может занять ~78 минут (6 шагов × 13 минут)
- Убедитесь, что сервер имеет достаточно ресурсов
- Рекомендуется запускать на отдельном тестовом окружении
- Сохраните результаты для анализа и отчетности
