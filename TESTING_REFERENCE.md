# Справочник по тестированию - Краткие ответы для презентации

**Назначение документа:** Этот документ содержит краткие объяснения механизмов работы всех видов тестирования и ответы на возможные вопросы преподавателя. Используйте его для быстрого поиска информации во время презентации.

---

## 1. Unit Tests (JUnit)

### Что это:
Модульное тестирование отдельных компонентов (сервисов, контроллеров) в изоляции от остальной системы.

### Механизм работы:
- Используется **H2 in-memory database** для изоляции данных
- **Mockito** для мокирования зависимостей (например, SecurityUtils, внешние API)
- Каждый тест создает свой контекст приложения через `@SpringBootTest`
- Тесты запускаются через Maven: `mvn clean test`

### Что проверяем:
- `PatientService` - логика создания, получения, обновления, удаления пациентов
- `VisitService` - логика работы с визитами
- `PatientController` - корректность работы REST API endpoints

### Где находятся:
- `src/test/java/com/medical/service/PatientServiceTest.java`
- `src/test/java/com/medical/service/VisitServiceTest.java`
- `src/test/java/com/medical/controller/PatientControllerTest.java`

### Возможные вопросы и ответы:

**Q: Почему используется H2, а не PostgreSQL?**  
A: H2 - это in-memory база данных, которая автоматически создается при запуске теста и удаляется после него. Это обеспечивает изоляцию тестов и скорость выполнения. Для интеграционных тестов с реальной БД есть отдельные скрипты.

**Q: Что такое Mockito и зачем он нужен?**  
A: Mockito позволяет создавать "моки" (заглушки) для зависимостей, чтобы тестировать компонент в изоляции. Например, мы мокируем SecurityUtils, чтобы не проверять аутентификацию в unit-тестах.

**Q: Сколько тестов написано?**  
A: 20 unit-тестов (11 для PatientService, 9 для VisitService, 5 для PatientController). Все тесты проходят успешно.

## 2. Volume Testing

### Что это:
Тестирование системы с большими объемами данных для проверки производительности и корректности работы при масштабировании.

### Механизм работы:
- Создается **1000 пациентов** в базе данных
- Выполняются операции создания, получения, поиска
- Измеряется время выполнения операций
- Проверяется целостность данных после создания больших объемов

### Что проверяем:
- Способность системы обрабатывать большие объемы данных
- Производительность операций (соответствие требованию ≤5 с из SRS PR-03)
- Целостность данных при больших объемах
- Корректность работы системы после массовых операций

### Где находится:
- `src/test/java/com/medical/performance/VolumeTestingTest.java`

### Тесты:
1. `testLargeVolumeOfPatients` - создание 1000 пациентов
2. `testLargeVolumeOfVisits` - создание множественных визитов
3. `testRetrievalPerformanceWithLargeDataset` - производительность получения 500 пациентов
4. `testDatabaseIntegrityWithLargeVolume` - целостность данных при 200 пациентах
5. `testConcurrentOperationsWithVolume` - операции после создания большого объема

### Возможные вопросы и ответы:

**Q: Почему только 1000 пациентов, а не 10,000?**  
A: 1000 пациентов достаточно для демонстрации работоспособности системы. Полное тестирование с 10,000+ записями требует значительно больше времени и ресурсов, но механизм тот же.

**Q: Как измеряется производительность?**  
A: Используется `System.currentTimeMillis()` до и после операции. Все операции выполняются за время, значительно меньшее 5 секунд (требование SRS PR-03).

**Q: Что происходит с данными после теста?**  
A: Данные создаются в H2 in-memory базе, которая автоматически удаляется после завершения теста. Это обеспечивает изоляцию и чистоту окружения.

## 3. Business Cycle Testing

### Что это:
End-to-end (сквозное) тестирование полного бизнес-процесса работы с пациентом от регистрации до завершения лечения.

### Механизм работы:
- Используется **полный стек приложения** (Spring Boot, H2)
- Тесты выполняют последовательность бизнес-операций:
  1. Регистрация пациента
  2. Создание визита
  3. Обновление статуса визита
  4. Создание контракта
  5. Сохранение и подписание контракта
  6. Создание ставки
  7. Создание анализа
  8. Обновление статуса анализа
- Проверяется целостность данных и корректность связей между сущностями на каждом шаге

### Что проверяем:
- Полный жизненный цикл пациента в системе
- Корректность связей между сущностями (пациент → визит → ставка → анализ)
- Правильность изменения статусов
- Целостность данных на всех этапах

### Где находится:
- `src/test/java/com/medical/integration/BusinessCycleTest.java`

### Тесты:
1. `testCompleteBusinessCycle` - полный цикл с одной операцией каждого типа
2. `testBusinessCycleWithMultipleVisits` - цикл с несколькими визитами

### Возможные вопросы и ответы:

**Q: Чем Business Cycle Testing отличается от Unit Testing?**  
A: Unit Testing проверяет отдельные компоненты в изоляции, а Business Cycle Testing проверяет интеграцию всех компонентов и выполнение полного бизнес-процесса от начала до конца.

**Q: Почему мокируется SecurityUtils?**  
A: Чтобы тест не требовал реальной аутентификации. В реальной системе проверка безопасности выполняется на уровне Spring Security, а здесь мы проверяем бизнес-логику.

**Q: Сколько шагов в полном цикле?**  
A: 11 шагов: регистрация пациента, проверка страховки, создание визита, обновление статуса визита, создание контракта, сохранение контракта, подписание контракта, создание ставки, создание анализа, обновление статуса анализа, проверка целостности данных.

## 4. API Functional Smoke Testing

### Что это:
Функциональное тестирование REST API через HTTP-запросы для проверки корректности работы endpoints.

### Механизм работы:
- Используется **curl** для отправки HTTP-запросов к работающему серверу
- Сервер должен быть запущен на порту 9314
- Выполняются POST, GET, PUT запросы к различным endpoints
- Проверяются HTTP статус-коды ответов (200, 201, 400, 404, 403)
- Используется **CSRF токен** для мутирующих запросов (POST, PUT)
- Проверяется содержимое JSON-ответов

### Что проверяем:
- FR-01: Регистрация пациента (POST /api/createPatient)
- FR-02: Создание визита (POST /api/createVisit)
- FR-03: Создание ставки (POST /api/createBet)
- FR-06-09: Работа с контрактами (создание, сохранение, подписание)
- FR-13-16: Работа с анализами (создание, обновление статуса)

### Где находится:
- `scripts/api-functional-smoke.sh`

### Как запускается:
```bash
./scripts/api-functional-smoke.sh
# или с параметрами:
BASE_URL=http://localhost:9314 ./scripts/api-functional-smoke.sh
```

### Возможные вопросы и ответы:

**Q: Почему используется curl, а не специальные инструменты?**  
A: curl - это стандартный инструмент командной строки, доступный везде. Он позволяет быстро проверить API и легко интегрируется в CI/CD. Для более сложных сценариев используется JMeter.

**Q: Как обрабатывается CSRF токен?**  
A: Сначала выполняется GET запрос к `/auth/csrf` для получения токена. Затем токен отправляется в заголовке `X-XSRF-TOKEN` для всех POST/PUT запросов. Это стандартный механизм защиты от CSRF атак в Spring Security.

**Q: Что означает "smoke testing"?**  
A: Smoke testing - это быстрая проверка основных функций системы, чтобы убедиться, что "не горит" (не падает). Мы проверяем ключевые endpoints и функциональные требования.

**Q: Как обеспечивается уникальность данных в тестах?**  
A: В именах пациентов добавляется timestamp, чтобы каждый запуск теста создавал уникальные записи и не возникало ошибок "пациент уже существует".

## 5. Database Integrity Testing

### Что это:
Проверка целостности данных в базе данных через прямые SQL-запросы.

### Механизм работы:
- Используется **PostgreSQL** в Docker контейнере
- SQL-скрипт с проверками выполняется через `psql` внутри контейнера
- Проверяются:
  - **NOT NULL constraints** - обязательные поля не пусты
  - **Foreign Key constraints** - все связи корректны
  - **Domain values** - значения соответствуют допустимому диапазону (например, gender только 'M' или 'F')
- Используется PL/pgSQL блок `DO $$ ... END $$` с `RAISE EXCEPTION` для проверок

### Что проверяем:
- 12 различных проверок целостности:
  - NOT NULL поля в таблицах patients, contracts
  - FK связи: patients→insurance_companies, visits→patients, bets→visits
  - FK связи: patient_analysis→patients, patient_analysis→analysis
  - FK связи: analysis_result→patient_analysis, analysis_bet→bets/patient_analysis
  - FK связи: contracts→patients, contracts→terms_and_conditions
  - Доменные значения (gender должен быть 'M' или 'F')

### Где находится:
- `scripts/db-integrity-checks.sql` - SQL-скрипт с проверками
- `scripts/run-db-integrity-checks.sh` - скрипт запуска

### Как запускается:
```bash
./scripts/run-db-integrity-checks.sh
```

### Возможные вопросы и ответы:

**Q: Почему используется PostgreSQL, а не H2 для этой проверки?**  
A: Database Integrity Testing проверяет реальную production-подобную базу данных. H2 может иметь некоторые отличия в реализации ограничений, поэтому важно проверить на той же БД, что используется в production (PostgreSQL).

**Q: Как работает механизм проверки?**  
A: SQL-скрипт выполняет SELECT запросы для поиска нарушений (например, COUNT записей с NULL или невалидными FK). Если найдены нарушения, выбрасывается RAISE EXCEPTION, что означает провал теста.

**Q: Что если в БД нет данных?**  
A: Скрипт проверяет структуру данных, а не их наличие. Если данных нет, все проверки пройдут успешно (нет нарушений). Для полноценной проверки нужны данные, которые создаются через API или SQL-скрипты.

**Q: Можно ли запускать это автоматически?**  
A: Да, скрипт `run-db-integrity-checks.sh` полностью автоматизирован. Он находит PostgreSQL контейнер и выполняет SQL-скрипт автоматически.

## 6. Security & Access Control Testing

### Что это:
Тестирование безопасности системы, проверка прав доступа для разных ролей пользователей.

### Механизм работы:
1. **Регистрация пользователей** с разными ролями (ADMIN, STAFF, DOCTOR, HEAD_DOCTOR, LAWYER, PATIENT)
2. **Аутентификация** каждого пользователя через `/auth/login`
3. **Получение CSRF токена** через `/auth/csrf`
4. **Выполнение операций** от имени каждого пользователя
5. **Проверка прав доступа**:
   - ADMIN/STAFF/HEAD_DOCTOR могут создавать пациентов
   - DOCTOR/LAWYER/PATIENT не могут создавать пациентов
   - Проверка на уровне `@PreAuthorize` в контроллерах
6. **Проверка CSRF защиты** - POST без токена должен получить 403
7. **Проверка SQL Injection / XSS** - попытка вставки вредоносного кода

### Что проверяем:
- Аутентификация работает корректно
- Авторизация по ролям работает согласно требованиям
- CSRF защита включена и работает
- SQL Injection и XSS атаки блокируются
- Неавторизованные пользователи не могут получить доступ к API

### Где находится:
- `scripts/security-access-tests.sh`

### Роли и их права:
- **ADMIN**: Полный доступ ко всем операциям
- **STAFF**: Может создавать пациентов, просматривать список
- **DOCTOR**: Может просматривать пациентов, создавать ставки, НЕ может создавать пациентов
- **HEAD_DOCTOR**: Полный доступ (как ADMIN)
- **LAWYER**: Работа с контрактами, НЕ может создавать пациентов
- **PATIENT**: Ограниченный доступ

### Возможные вопросы и ответы:

**Q: Как реализована авторизация?**  
A: Используется Spring Security с методом `@PreAuthorize` в контроллерах. Каждый endpoint проверяет роль пользователя перед выполнением операции.

**Q: Что такое CSRF и зачем он нужен?**  
A: CSRF (Cross-Site Request Forgery) - это атака, когда злоумышленник заставляет авторизованного пользователя выполнить нежелательное действие. Защита через токен гарантирует, что запрос отправлен с легитимной страницы.

**Q: Как проверяется SQL Injection?**  
A: В поле firstName отправляется строка с SQL кодом (например, `'; DROP TABLE patients; --`). Система должна обработать это как обычную строку, а не выполнить как SQL. Проверяем, что валидация входных данных работает корректно.

**Q: Почему некоторые роли не могут создавать пациентов?**  
A: Согласно бизнес-логике, только регистраторы (STAFF), администраторы (ADMIN) и заведующие (HEAD_DOCTOR) могут регистрировать новых пациентов. Врачи (DOCTOR) работают с существующими пациентами, а пациенты и юристы имеют свои ограниченные функции.

**Q: Что делать, если тест на CSRF не проходит?**  
A: Нужно проверить, что CSRF защита включена в `SecurityConfig` и что токен корректно отправляется в заголовке `X-XSRF-TOKEN`.

## 7. Performance Profiling

### Что это:
Измерение производительности ключевых операций системы для проверки соответствия требованиям SRS PR-03.

### Механизм работы:
1. **Подготовка данных**: Создание тестового пациента, визита, контракта
2. **30 последовательных измерений** для каждой операции:
   - GET /api/getPatients - загрузка списка пациентов
   - GET /api/getPatient - открытие карты пациента
   - GET /api/getPatients с фильтром - поиск по имени
   - POST /api/createBet - создание ставки
3. **Вычисление метрик**:
   - Среднее время (mean)
   - Медиана (median)
   - Минимум и максимум (min, max)
   - 90-й и 95-й перцентили (p90, p95)
   - Процент операций ≤5 секунд

### Что проверяем:
- Соответствие требованию **SRS PR-03**: 90% операций должны выполняться ≤5 секунд
- Производительность ключевых операций в нормальных условиях
- Стабильность времени отклика

### Где находится:
- `scripts/performance-profiling.sh`

### Требования:
- **PR-03**: Система должна поддерживать время отклика не более 5 секунд для 90% операций

### Возможные вопросы и ответы:

**Q: Почему именно 30 измерений?**  
A: 30 измерений достаточно для статистической значимости и получения репрезентативных данных о производительности. Это стандартная практика в профилировании производительности.

**Q: Что такое перцентили (p90, p95)?**  
A: p90 означает, что 90% запросов выполняются быстрее этого времени. p95 - что 95% запросов быстрее. Это более информативно, чем среднее значение, так как показывает производительность для большинства пользователей.

**Q: Как интерпретировать результаты?**  
A: Если 90% операций выполняются ≤5 секунд, значит требование PR-03 выполнено. Если p95 значительно выше среднего, это может указывать на проблемы с производительностью при пиковой нагрузке.

**Q: В чем разница между Performance Profiling и Load Testing?**  
A: Performance Profiling измеряет производительность при нормальной нагрузке (1 пользователь, 30 запросов). Load Testing проверяет поведение системы под высокой нагрузкой (50+ одновременных пользователей).

## 8. Load Testing (JMeter)

### Что это:
Нагрузочное тестирование для проверки поведения системы под максимальной декларированной нагрузкой.

### Механизм работы:
1. **JMeter** создает виртуальных пользователей (потоки)
2. **4 типа пользователей**:
   - 20 пользователей: Просмотр списка пациентов (GET /api/getPatients, GET /api/getPatient)
   - 15 пользователей: Управление пациентами (POST /api/createPatient)
   - 10 пользователей: Работа со ставками (GET /api/getBetPatients, POST /api/createBet)
   - 5 пользователей: Внешние API (POST /api/insurance/check)
3. **Профиль нагрузки**:
   - Ramp-up: 300 секунд (5 минут) - постепенное увеличение с 0 до 50 пользователей
   - Hold: 2100 секунд (35 минут) - удержание нагрузки на уровне 50 пользователей
   - Ramp-down: автоматический после завершения
4. **Измерение метрик**:
   - Время отклика (average, median, p90, p95, p99)
   - Throughput (запросов/сек)
   - Процент ошибок
   - Размер ответа

### Что проверяем:
- Система должна справляться с 50 одновременными пользователями
- Процент ошибок должен быть ≤1%
- Время отклика должно быть ≤5 секунд для 90% запросов
- Стабильность системы под нагрузкой

### Где находится:
- `jmeter-tests/load-test/load_test_plan.jmx` - тестовый план JMeter
- `jmeter-tests/run_load_test.sh` - скрипт запуска

### Как запускается:
```bash
cd jmeter-tests
./run_load_test.sh 50
```

### Возможные вопросы и ответы:

**Q: Почему используется JMeter?**  
A: JMeter - это стандартный инструмент для нагрузочного тестирования с графическим интерфейсом и возможностью автоматизации. Он позволяет легко настраивать профили нагрузки и собирать детальную статистику.

**Q: Как работает аутентификация в JMeter?**  
A: Используется HTTP Authorization Manager с Basic Authentication (username: admin, password: password). Также используется HTTP Cookie Manager для сохранения сессии и HTTP Header Manager для отправки CSRF токена.

**Q: Что такое ramp-up и зачем он нужен?**  
A: Ramp-up - это постепенное увеличение нагрузки от 0 до целевого количества пользователей. Это позволяет системе адаптироваться к нагрузке постепенно, а не получать мгновенный удар. Это более реалистично имитирует реальное использование.

**Q: Как извлекается CSRF токен?**  
A: Используется JSON Extractor в JMeter, который парсит JSON ответ от `/auth/csrf` и извлекает значение `token` в переменную `${csrf_token}`. Затем эта переменная используется в заголовке `X-XSRF-TOKEN` для POST запросов.

**Q: Почему в тесте 5% ошибок для "Get Bet Patients"?**  
A: Это связано с тем, что для создания ставки нужен существующий визит со статусом Accepted. Если визитов недостаточно, некоторые запросы могут не найти данные. Это нормальное поведение для нагрузки, но стоит оптимизировать данные для теста.

**Q: Как интерпретировать результаты?**  
A: 
- **Throughput 958 req/s** - система обрабатывает почти 1000 запросов в секунду
- **Average 5ms** - среднее время отклика очень низкое
- **p95 22ms** - 95% запросов выполняются за 22 миллисекунды
- **Error rate 0.023%** - практически нет ошибок

## 9. Stress Testing (JMeter)

### Что это:
Стресс-тестирование для определения пределов системы, точки деградации и характеристик восстановления.

### Механизм работы:
1. **Пошаговое увеличение нагрузки**: 50 → 75 → 100 → 125 → 150 → 200 пользователей
2. **Для каждого шага**:
   - Ramp-up: 3 минуты (180 секунд)
   - Hold: 10 минут (600 секунд)
   - Автоматическое измерение метрик
3. **Критерии остановки** (когда зафиксировать точку деградации):
   - Процент ошибок 5xx > 5%
   - ИЛИ Latency p99 > 30 секунд
4. **Автоматизация**: Скрипт `run_stress_test.sh` автоматически изменяет количество потоков в JMeter тестовом плане и запускает тесты последовательно

### Что проверяем:
- Пределы устойчивости системы
- Точку деградации (когда система начинает работать нестабильно)
- Время восстановления после снятия нагрузки
- Поведение системы при экстремальной нагрузке

### Где находится:
- `jmeter-tests/stress-test/stress_test_plan_base.jmx` - базовый тестовый план
- `jmeter-tests/run_stress_test.sh` - скрипт автоматизации
- `jmeter-tests/stress-test/update_thread_counts.py` - Python скрипт для изменения количества потоков

### Как запускается:
```bash
cd jmeter-tests
./run_stress_test.sh
```

### Возможные вопросы и ответы:

**Q: В чем разница между Load Testing и Stress Testing?**  
A: Load Testing проверяет систему при декларированной максимальной нагрузке (50-100 пользователей). Stress Testing постепенно увеличивает нагрузку за пределы нормальной работы, чтобы найти точку, когда система начинает деградировать (150-200+ пользователей).

**Q: Как автоматизируется изменение нагрузки?**  
A: Используется Python скрипт `update_thread_counts.py`, который парсит XML файл JMeter, находит элементы с количеством потоков и изменяет их согласно текущему шагу теста. Затем JMeter запускается в non-GUI режиме.

**Q: Что такое точка деградации?**  
A: Это момент, когда система перестает справляться с нагрузкой: увеличивается время отклика, появляются ошибки, падает throughput. Цель - найти эту точку, чтобы знать пределы системы.

**Q: Почему тест был прерван на 50 пользователях?**  
A: Тест был прерван вручную для демонстрации. Полный тест занимает около 78 минут (6 шагов × 13 минут). Результаты показывают, что система стабильна при 50 пользователях, поэтому можно продолжить с большей нагрузкой.

**Q: Что делать, если система не достигает точки деградации при 200 пользователях?**  
A: Это хороший знак - система очень масштабируема. Можно продолжить увеличивать нагрузку (250, 300, 500 пользователей) до достижения точки деградации или ограничений инфраструктуры.

**Q: Как измеряется время восстановления?**  
A: После завершения стресс-теста система должна вернуться к нормальному времени отклика. Время восстановления - это период от окончания нагрузки до нормализации метрик. Для полноценного измерения нужно добавить мониторинг после завершения теста.

## 11. Быстрые ответы на технические вопросы

### Q: Что такое CSRF токен и как он работает?
**A:** CSRF (Cross-Site Request Forgery) токен - это уникальный токен, который сервер генерирует для каждой сессии. Клиент должен отправлять этот токен в заголовке `X-XSRF-TOKEN` для всех мутирующих запросов (POST, PUT, DELETE). Это защищает от атак, когда злоумышленник пытается выполнить действие от имени авторизованного пользователя.

### Q: Как работает аутентификация в системе?
**A:** Используется Spring Security с Basic Authentication. Пользователь отправляет username и password через заголовок `Authorization: Basic <base64>`. Сервер создает сессию и возвращает cookies. Для получения CSRF токена необходимо сначала пройти аутентификацию.

### Q: Почему в некоторых тестах используется H2, а в других PostgreSQL?
**A:** 
- **H2** используется для unit и integration тестов, так как быстро запускается и обеспечивает изоляцию
- **PostgreSQL** используется для database integrity тестов, чтобы проверить реальную production-подобную базу

### Q: Как JMeter извлекает динамические данные (patientId, visitId)?
**A:** Используется JSON Extractor, который парсит JSON ответ и извлекает значение по JSON Path (например, `$[0].id` для первого элемента массива). Извлеченное значение сохраняется в переменную JMeter (например, `${patientId}`) и используется в последующих запросах.

### Q: Что такое ramp-up в нагрузочном тестировании?
**A:** Ramp-up - это период постепенного увеличения количества виртуальных пользователей от 0 до целевого значения. Например, ramp-up 5 минут означает, что за 5 минут количество пользователей постепенно увеличится с 0 до 50. Это имитирует реалистичное увеличение нагрузки.

### Q: Как интерпретировать p90, p95, p99 в результатах тестов?
**A:**
- **p90**: 90% запросов выполняются быстрее этого времени
- **p95**: 95% запросов выполняются быстрее этого времени  
- **p99**: 99% запросов выполняются быстрее этого времени

Чем выше перцентиль, тем более экстремальные случаи он показывает. p99 показывает производительность даже в худших условиях.
